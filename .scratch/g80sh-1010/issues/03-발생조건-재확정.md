# 03 — 발생 조건 재확정: 원격은 조건이 아니었다

Type: task
Status: resolved
Blocked by: —

## Question

보고서 4-3 「확정된 조건」은 *원격 접속 후 + 절전*이다. **09-19 데이터가 이를 부정한다.**

```
12:26:13  monitors asleep - screen off     ← 폭풍 시작
          12시 57 · 13시 101 · 14시 95 · 15시 100 · 16시 53   합 406건
16:30:33  display power: on
16:31:25  마지막 1010                       ← 폭풍 끝
```

이 4시간 동안 크롬 원격 접속은 없었다. `RemoteDisplaySwitch.log` 09-19 전량:

```
11:41:15  watcher started
16:30:35  REMOTE layout      ← 오늘 유일한 원격, 40초
16:31:19  remote ended
```

동시에 **화면 꺼짐만으로도 충분하지 않다**:

```
00:22:18 ~ 01:01:36  화면 꺼짐 39분   →  1010    0건
12:26:13 ~ 16:30:33  화면 꺼짐 4시간  →  1010  406건
```

보고서 4-2의 대조 실험은 "원격 해제 후"만 관찰했고 **"원격 없이 절전"을 대조군으로 두지
않았다.** 원격은 조건이 아니라 절전을 유발하는 흔한 경로였을 가능성이 크다.

답해야 할 것:

1. 09-08 이후 모든 화면 꺼짐 구간을 원격 이력과 대조했을 때, 원격 유무가 1010 발생률을
   가르는가. (`CaseDisplay.log` × `RemoteDisplaySwitch.log` × Kernel-PnP 1010)
2. 가르지 않는다면, 폭풍이 나는 절전 구간과 나지 않는 절전 구간을 가르는 제3변수는
   무엇인가.
3. 09-18 17:36 이후 정지와 09-19 12:26 재발을 같은 변수로 설명할 수 있는가.

## 관측 기록

### 실험 A — 09-19 16:45, 강제 끄기

```
12:26:13  자연 절전(전원 정책 타임아웃)  →  12:27:00.707  첫 SAM7B0C 1010   (47초)
16:45:19  강제 SC_MONITORPOWER off       →  +339초까지                    0건
```

09-18 21:03의 강제 끄기도 0건이었으나 그날은 이미 폭풍이 끝난 뒤(17:36 정지)라 근거가
약했다. 09-19는 16:31까지 폭풍이 돌던 당일이라 대조가 훨씬 강하다.

설명이 세 갈래로 갈렸다:

1. **강제 끄기 경로라서** — `SC_MONITORPOWER`는 전원 정책 타임아웃과 다른 경로로 DPMS를
   내린다. 방아쇠가 전자에만 있을 수 있다. (DP 메인 링크를 내리느냐 아니냐의 차이)
2. **16:31:28의 `RESET mode=rewake -> wake=2` 때문** — `RemoteDisplaySwitch`가 원격 종료
   직후 모니터를 재기동했다. 이것이 모니터 상태를 초기화했을 수 있다.
3. **저녁에 잦아드는 시간대라서** — 09-18도 같은 모양으로 꺼졌다:

   ```
   09-18   15시 28   16시 22   17시 15   18시 2   19시 1   20시 1   21시 2
   09-19   15시 100  16시 53 (16:31 마지막)
   ```

### 실험 B — 09-19 16:53, 자연 절전 (A를 가르는 실험)

`VIDEOIDLE`(AC)을 900초 → 60초로 줄이고 16:52:17에 화면을 깨워, 전원 정책이 자연 경로로
끄게 했다.

```
16:53:17  display power: off        ← 전원 정책 타임아웃 (자연 경로)
16:53:20  monitors asleep - screen off
          +219초까지                 1010  0건
```

**결과: 재현 안 됨. (1) 기각.**

기준선 대비: 12:26:13 자연 절전에서는 **47초** 만에 첫 건이 났고, 09-08 이후 관측된
최대 간격도 175초였다. 219초 무사고는 우연이 아니다.

즉 **끄기 명령의 경로(`SC_MONITORPOWER` vs 전원 정책)는 방아쇠가 아니다.** 같은 자연
경로로 껐는데 12:26에는 47초 만에 터지고 16:53에는 터지지 않았다.

남은 설명은 (2)와 (3)이다. 둘 다 "절전에 들어가는 방식"이 아니라 **"절전에 들어가기 전의
상태"**를 가리킨다. **조건은 전환 순간이 아니라 상태에 있다.**

로그: `_evidence\forced-off-test.log`, `_evidence\natural-sleep-test.log`

### 되돌릴 것

- `VIDEOIDLE`(AC) 현재 **60초**. 원래 값은 **900초**. 재현 기회를 늘리려고 낮춰 둔 것이므로
  관측이 끝나면 되돌린다.
  `powercfg /setacvalueindex SCHEME_CURRENT SUB_VIDEO VIDEOIDLE 900; powercfg /setactive SCHEME_CURRENT`

## 아직 답하지 못한 것

- 00:22:18 ~ 01:01:36 화면 꺼짐 39분 구간은 **0건**이었다. 같은 절전인데 왜 하나도 나지
  않았는가. 이 구간은 09-18 22:36 재부팅 뒤, 09-18 17:36 정지가 이어지던 중이다. 즉
  **정지 상태가 재부팅을 넘어 유지됐고, 02:18 종료 + 11:40 부팅 뒤에 깨졌다.**
  22:36은 재시작, 02:18은 9시간 전원 차단이었다는 차이가 있다.
- (2)를 가르려면 `RESET mode=rewake`를 한 번 더 태우고 그 뒤 절전을 관찰해야 한다.
  (3)을 가르려면 다음 폭풍 시간대(부팅 후 첫 절전)를 기다려야 한다. 둘은 서로 배타적이지
  않다.

## 【중요】 Kernel-Power 566 — 화면 전원 전환의 OS 정식 기록

09-19 17:37 발견. `System` 로그, 공급자 `Microsoft-Windows-Kernel-Power`, **이벤트 ID 566**.
"시스템 세션이 N에서 M (으)로 전환되었습니다" 형태로 화면 전원 전환을 남긴다.
**2026-08-08부터 보존돼 있다** (System 로그 최고 기록 08-08 03:41:54).

CaseDisplay.log보다 나은 근거다 — Windows 네이티브이고, 제3자 도구가 아니며, 훨씬 길다.

홀수 전환(0→1, 3→4, 6→7 …)이 **꺼짐**, 짝수 전환(1→3, 4→6 …)이 **켜짐**이다.
CaseDisplay.log와 대조해 확인했다:

```
09-19 12:26:11  566 0→1   ==  CaseDisplay "display power: off"
09-19 16:30:33  566 1→3   ==  CaseDisplay "display power: on"
09-19 16:53:17  566 3→4   ==  CaseDisplay "display power: off"
```

### 폭풍이 566 꺼짐 구간과 정확히 일치한다

```
09-18 09:27:55  566 6→7  꺼짐
                09시 53 · 10시 89 · 11시 94 · 12시 96 · 13시 86 · 14시 92
09-18 15:04:30  566 7→9  켜짐  →  15시 26 으로 급감

09-19 12:26:11  566 0→1  꺼짐
                12~16시 406건
09-19 16:30:33  566 1→3  켜짐  →  16:31:25 마지막
```

### 강제 끄기는 566을 남기지 않는다 — 실험 A 음성의 진짜 이유

```
16:45:18  CaseDisplay "display power: off"   ← 화면은 실제로 꺼졌다
16:45~16:52  Kernel-Power 566                 0건   ← OS 는 아무 전환도 하지 않았다
16:53:17  자연 절전                            566 3→4 있음
```

`SC_MONITORPOWER`는 모니터를 어둡게 할 뿐 **전원 관리자의 디스플레이 전원 상태 전환을
일으키지 않는다.** "경로가 다르다"는 앞의 서술보다 훨씬 정확한 설명이다.

→ **방아쇠는 OS 의 디스플레이 전원 상태 전환(566)에 걸려 있다.**
   다만 566 꺼짐이 곧 폭풍은 아니다 — 16:53:17 은 566 이 있었는데도 0건이었다.
   **566 꺼짐은 필요조건이고, 충분조건이 아니다.**

### 곁가지 이상 — 부팅 후 `VIDEOIDLE` 900초가 실제로 걸리지 않았다

```
17:18:18  부팅
17:19:59  마지막 입력
17:34:59  900초 경과 — 꺼졌어야 함
17:40:24  유휴 1225초, 566 0건, 잠금 아님, DISPLAY 전원 요청 없음
17:40:58  VIDEOIDLE 900 -> 60 적용 (+ /setactive)
17:40:59  566 0→1 발화   ← 1초 만에
```

타이머 자체는 살아 있다. 전원 정책을 **다시 적용**하자 즉시 발화했다.
즉 이번 부팅 세션에 900초가 실제로 걸려 있지 않았다. 값은 `0x384`로 조회되는데
전원 관리자는 그것으로 타이머를 돌리지 않고 있었다.

증상과 직접 관계가 있는지는 미확인. 다만 **관측을 방해하므로** 기록해 둔다 —
"화면을 안 끄면 폭풍도 없다"를 "증상이 사라졌다"로 오독하면 03을 또 틀리게 만든다.

### 이 발견이 03에 주는 것

앞서 "조건은 전환 순간이 아니라 절전 전 상태에 있다"고 좁혔는데, 566이 그 축을
**측정 가능하게** 만든다. 08-08 이후 모든 566 꺼짐 구간을 1010 발생 건수와 대조하면
"폭풍이 나는 절전"과 "안 나는 절전"을 가르는 변수를 통계로 찾을 수 있다.
이것이 03의 남은 작업이다.
