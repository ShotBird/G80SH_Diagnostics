# 06 — AMD EDID 에뮬레이션 검증 실험을 어떻게 설계할 것인가

Type: grilling
Status: resolved
Blocked by: —

## Question

04가 남긴 단 하나의 미확인 항목을 이 PC에서 직접 가른다:

**에뮬레이션이 EDID 내용만 대체하는가, child status(HPD)까지 connected로 고정하는가.**

- HPD까지 고정 → 재열거 자체가 사라진다. **근원개선 성립.**
- EDID만 대체 → HPD가 끊기는 순간 `EDID_OVERRIDE`와 같은 이유로 무력. 후보 폐기.

## 실험 자체는 이미 설계돼 있다

`_evidence\research_AMD_EDID_에뮬레이션.md` 6장:

1. AMD Software → Displays 탭에 `EDID Emulation`이 보이는지 먼저 본다. 보이면 GUI로 끝난다.
2. 현재 실제 EDID 384바이트(`SAM` / `0x7B0C`)를 그대로 내보낸다.
3. DP connector 0에 `ADL2_Adapter_ConnectionData_Set` → `ADL2_Adapter_EmulationMode_Set`.
   보수적으로 `ADL_EMUL_MODE_ON_DISCONNECTED(2)`부터, 필요하면 `ALWAYS(3)`.
4. 절전으로 보낸 뒤 1010이 `SAM7B0C` / `Default_Monitor`에 대해 찍히는지 본다.
5. 되돌리기: `ADL2_Adapter_ConnectionData_Remove` → `EmulationMode_Set(..., 0)`.

## 그래서 결정할 것은 실험 절차가 아니라 이것들이다

### (1) 판정에 양성 대조군이 필요하다 — 이게 가장 큰 문제

4항의 판정 기준 "1010이 안 찍히면 성립"은 **폭풍이 도는 중에만 의미가 있다.**
09-19 16:31 이후로는 에뮬레이션과 무관하게 아무것도 안 찍힌다. 그 상태에서 실험하면
반드시 "성립"이라는 거짓 양성이 나온다.

03에서 이미 같은 함정을 두 번 밟았다(실험 A·B 모두 폭풍이 끝난 뒤였다).

→ **폭풍이 도는 중에 켜서 멎는지 보는 설계**여야 한다. 즉 다음 폭풍(내일 부팅 후 첫 절전)을
기다렸다가, 폭풍 확인 → 에뮬레이션 켜기 → 멎는지 관찰 → 끄기 → 다시 나는지 관찰.
켜고 끄는 것을 한 폭풍 안에서 왕복해야 시간대 효과와 갈린다.

### (2) 되돌릴 수 없는 상황에 대한 대비

AMD 공식 릴리스 노트에 **"EDID 에뮬레이션 상태에서 Modern Standby 복귀 후 blank-out"**,
**"EDID 에뮬레이션에서 MSB 진입 실패"**가 알려진 이슈로 명시돼 있다
(우회키 `DalEdidReadDeferralTime=1`). 이 케이스가 정확히 절전 시나리오다.

화면이 안 켜지면 원격도 콘솔도 막힌다. 결정할 것:
- 복구 경로를 어디까지 준비할 것인가 (되돌리기 스크립트를 작업 스케줄러 `onstart`에 걸어둘 것인가,
  안전 모드까지 상정할 것인가)
- `ON_DISCONNECTED`만으로 갈 것인가, `ALWAYS`까지 갈 것인가
- 실패 시 자동 복구를 몇 분 뒤에 걸 것인가

### (3) 02와의 순서

02(선후 판정)의 답이 "모니터 선행"으로 나오면 ②는 애초에 성립 가능성이 낮아진다.
02를 기다렸다가 06을 할 것인가, 병행할 것인가.

→ 둘 다 **다음 폭풍**을 기다린다는 점은 같다. 같은 폭풍에서 02 캡처를 먼저 받고
(순환 세션은 이미 떠 있다), 그 다음 같은 폭풍 안에서 06 왕복을 하는 것이 자연스럽다.
다만 에뮬레이션을 켜면 그 뒤 캡처의 의미가 달라지므로 순서를 못 바꾼다.

### (4) 기전 가설의 무게중심

04의 부수 발견: 최근 3일 1010은 `Default_Monitor` 413건이 지배적이고, 보고서 8항이
기전으로 지목한 `SAM7B0B`/`SAM7B11`은 09-08 이후 전체에서 2건/1건뿐이다.
06의 판정 지표를 `SAM7B0C` 1010만 볼 것인가, `Default_Monitor`까지 볼 것인가.

## Answer — ADL 쓰기 경로가 막혀 있다. ② 실행 불가

09-19 18:13 실측. `_evidence\emul-test.log`, `_evidence\edid-emul.log`
도구: `tools\g80sh_edid_emul.py`, `tools\g80sh-emul-test.ps1`

### 1차 시도(18:01) — 무효

왕복 실험을 돌렸으나 `ConnectionData_Set`이 `rc=-8`로 실패했고, 스크립트가 종료 코드를
확인하지 않고 관측 단계로 넘어갔다. "ON 7건 vs OFF 9건"은 **둘 다 에뮬레이션이 꺼진
상태의 숫자**이므로 비교가 성립하지 않는다. 스크립트 결함이었다.

### 2차 — 쓰기 API 전수 시도, 전부 거부

```
REAL connType=4 size=384 SAM 0x7B0C
SupportedConnections mask=0x1610  (bit4 = DisplayPort 지원)

ConnectionData_Set  REAL connType 그대로 (4, 384B)  -> rc=-8
ConnectionData_Set  DP(4), 384B                     -> rc=-8
ConnectionData_Set  DP(4), props 없이               -> rc=-8
ConnectionData_Set  REAL connType, base 128B만      -> rc=-8
EmulationMode_Set   mode 2 (ON_DISCONNECTED)        -> rc=-8
EmulationMode_Set   mode 3 (ALWAYS)                 -> rc=-8
EmulationMode_Set   mode 1 (ON_CONNECTED)           -> rc=-8
```

`-8` = `ADL_ERR_NOT_SUPPORTED`. 인자 문제가 아니다 — `connType=4`는 `ConnectionData_Get`이
REAL로 돌려준 값 그대로이고, `SupportedConnections`도 이 커넥터에서 DP를 지원한다고 답한다.
**쓰기 API 자체가 차단돼 있다.**

### 04 의 근거 정정

04는 `ADL2_Adapter_EDIDManagement_Caps` → `supported=1` 을 근거로 "소비자용 Adrenalin 에서
쓸 수 있다"고 판정했고, "Pro 전용인 것은 *Global EDID Persistence* 쪽"이라고 갈랐다.
**그 판정은 틀렸다.** caps 비트는 조회에 1을 돌려주지만 **쓰기 경로도 Pro 전용**이다.
caps 비트만으로 가용성을 판단하면 안 된다는 사례로 남긴다.

### 남은 길 — AMD Software GUI

리서치가 `RadeonSoftware.exe` 안에서 `EDID.qml` / `EDIDEmulate.qml` 과
"Manage EDID emulation for display connections…" 문자열을 실물로 확인했다.
GUI가 ADL 이 아닌 다른 경로(드라이버 사설 인터페이스)를 쓸 가능성이 남아 있다.

**확인 비용**: 화면을 켜고 AMD Software → Displays 탭을 직접 봐야 한다.
화면을 켜면 폭풍이 멎으므로, 항목이 **있는지/활성인지만** 보고 끄는 식으로 분리해야 한다.
켠 상태에서 설정만 해두고 다시 절전에 보내면 판정은 가능하다.

### 부수 관측 — 절전 중 EDID 읽기가 간헐적으로 실패한다

```
17:58:27  ConnectionData_Get  connIdx=0/1 모두 384B 정상 (화면 꺼짐, 폭풍 중)
18:12:xx  ConnectionData_Get  모든 커넥터에서 0건
18:13:01  ConnectionData_Get  다시 384B 정상
```

ADL 조회 수준에서도 EDID 를 읽었다 못 읽었다 한다. `Default_Monitor` 폴백 1,294건과
같은 축의 현상으로 보인다. 02가 잡은 "드라이버가 스스로 자식 소실을 판단한다"와도 맞는다.

### 이 결과가 도착지에 주는 영향

**(c) 근원개선의 후보 ②가 막혔다. ①(모니터 펌웨어)만 남는다.**

→ 범위 밖으로 두었던 (b) 제출 트랙의 비중이 커진다. 맵의 도착지를 다시 볼 필요가 있다.
