## Answer

### 1. 810 의 스택으로는 못 가른다 — 한 단계 비동기다

```
ntoskrnl!PnpRequestDeviceAction
ntoskrnl!IopProcessInvalidateBusRelationsRequest
ntoskrnl!IopInvalidateBusRelationsWorker      ← 커널 작업자 스레드
ntoskrnl!ExpWorkerThread
```

`IoInvalidateDeviceRelations` 는 요청을 작업 큐에 넘기고, 810 은 그 작업자에서 찍힌다.
원 호출자는 스택에 남지 않는다. **16 이 제안한 방법은 틀렸다.**

### 2. 진짜 앞단은 AMD 드라이버의 "커넥터 변경" 신호다

DxgKrnl `Base` 키워드에 스택을 걸자 **두 사이클 모두 Q1 0.2~0.3ms 앞에 같은 경로**가 나왔다.

```
dxgkrnl!DpiIndicateConnectorChangeWorkItem           ← AMD 가 DxgkCbIndicateConnectorChange 로 신호 → 작업 큐
  dxgkrnl!DxgkQueryConnectionChanges
    dxgkrnl!DpiDxgkDdiQueryConnectionChange          ← "무엇이 바뀌었나" AMD 에 질의
    dxgkrnl!DpiPdoHandleChildConnectionChange
      DdiQueryDeviceDescriptor (EDID)
→ Kernel-PnP 810 → 220 → 1010
```

### 3. AMD 가 보고한 내용 — G80SH 만 "빠졌다 곧바로 다시 붙었다"

`DdiQueryConnectionChange` 페이로드(`ConnectionStatus`: 8 = MonitorStatusDisconnected,
10 = MonitorStatusConnected / `TargetId` 260 = G80SH, 256 = G50F):

```
            사이클 1        사이클 2        AMD 가 보고한 것 (대상 260 = G80SH)
Q1 직전   22.436463 s     68.978059 s     8  모니터 분리
          22.436574 s     68.978233 s     10 모니터 연결   ← 0.11~0.17ms 뒤. 분리+연결 한 묶음
Q1        22.436667 s     68.978295 s     → SAM7B0C 제거, Default_Monitor(EDID 못 읽음) 추가
Q2 직전   22.650660 s     69.231870 s     8  모니터 분리
Q3 직전   25.973689 s     72.559082 s     10 모니터 연결   ← 3.3초 뒤
```

**같은 시각 전 포트 일괄 보고에서 G50F(256)는 늘 10(연결)이다.** 같은 GPU·같은 드라이버다.

→ 16 의 "Q1 직전에 10011 이 없다"는 **드라이버가 스스로 판단했다는 뜻이 아니었다.**
10011(StatusChangeNotify)이 안 찍히는 경로(ConnectorChange 계열)로 **AMD 드라이버가
"G80SH 가 분리됐다가 다시 연결됐다"는 변경을 올리고 있다.** 02 의 해석
("모니터가 링크를 끊어 알린 것이 아니다")은 **정정한다** — 알림 통로가 달랐을 뿐,
드라이버는 연결 변경을 감지해서 보고했다.

### 4. 남은 것 — AMD 드라이버 안쪽은 못 들어간다

- AMD 가 "분리"를 **무엇으로** 알았는지(HPD 핀 신호 / AUX·DPCD 읽기 실패 / 자체 점검)는
  `amdkmdag.sys` 에 공개 심볼이 없어 스택이 주소로만 나온다. 여기가 PC 쪽 관측의 끝이다.
- **관찰(표본 2)**: 두 사이클 모두 Q1 **1.39~1.41초 전**에 AMD 의 전 포트 일괄 보고가 있었다
  (21.042 → 22.437, 67.567 → 68.978). 일괄 보고는 Q1 없이도 온다(10.68, 54.96, 97.78초).
  AMD 쪽 주기 점검이 모니터를 건드리고 1.4초 뒤 모니터가 분리 신호를 내는 형태일 수 있다.
  판정하려면 표본이 더 필요하다 — `tools\g80sh-stack-capture.ps1` 을 폭풍 중에 몇 번 더 돌리면 된다.

## AMD 설정으로 해결되는가 (사용자 질문, 2026-09-23)

**설정으로는 안 된다고 본다.** 근거:

1. AMD 는 "G80SH 가 분리/연결됐다"는 **연결 상태 변화를 전달하고 있을 뿐**이고, 같은 조건의 G50F 는
   분리로 보고되지 않는다. 설정이 바꾸는 것은 전달 이후의 처리다.
2. 전달을 막는(= 항상 연결로 취급하는) 기능은 AMD 소비자 드라이버에 없다 —
   EDID 에뮬레이션 쓰기 전 변형 `-8 NOT_SUPPORTED`, GUI 항목 없음(06).
   `HpdAwarenessAlwaysConnected` 는 드라이버만 선언할 수 있다(04).
3. 이미 태운 AMD 쪽 변수: FreeSync 끄기(09-4), 드라이버 완전 재설치·Factory Reset(08),
   DSC·DP 버전(14·15 — 모니터 OSD 지만 GPU 링크 구성을 통째로 바꿨다). 전부 무효.
4. 설령 AMD 가 드라이버에서 이 신호를 무시하게 만든다 해도 그것은 **증상을 가리는 우회책**이다
   (상시규칙 1). 모니터가 절전 중 분리 신호를 내는 동작은 그대로 남는다.

단 하나 열린 곳: 4번 관찰(AMD 일괄 점검 1.4초 뒤 발생)이 확정되면 "AMD 의 주기 점검이
방아쇠, 모니터의 오응답이 원인"이 된다. 그래도 **해결 주체는 모니터**(DP 규격상 싱크는
절전 중 AUX 요청에 링크를 끊지 않고 응답해야 한다)이고, AMD 에는 "점검 빈도" 설정이 노출돼 있지 않다.
