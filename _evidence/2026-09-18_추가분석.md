## 5. 제3자 도구는 원인이 아니다 (삼성 측 반박 대비)

이 PC에는 `RemoteDisplaySwitch.ps1`(디스플레이 구성 감시자)과
`CaseDisplay`(케이스 LCD 구동)가 상주한다. 원인이 아님을 두 가지로 확인했다.

**① 코드 레벨**

`RemoteDisplaySwitch.ps1` rev.6는 G80SH가 대기 상태일 때 복구 동작을 하지 않는다:

```powershell
$homeAsleep = -not ($avail -contains $G80)
if ($homeAsleep -and -not $pendingReset) {
    if (-not $asleepLogged) { Log "...skip repair..." }   # 아무 동작 없음
}
```

상태 조회에 쓰는 `Get-Available`은 `QueryDisplayConfig`(CCD API) 호출로 **읽기 전용**이며
디스플레이 구성을 변경하지 않는다.

**② 타이밍**

1010 이벤트가 감시자의 감지보다 **0.3~1.5초 먼저** 기록된다:

```
12:00:40.729  Kernel-PnP 1010          ← 먼저
12:00:41      감시자 "not attachable"   ← 나중
12:00:45      감시자 "monitor back"     ← 4초 뒤 복귀
```

감시자는 현상을 따라가는 쪽이지 유발하는 쪽이 아니다.
"연결 해제 4~5초 뒤 재연결"이라는 기존 진술도 이 로그로 뒷받침된다.

**③ `SetDisplayConfig` 호출도 무관**

구성 재적용(`SetDisplayConfig`, `SDC_SAVE` 포함)이 증상을 좌우하는지 검증했다.
로그에 남은 `HOME layout` 호출 28회 중 마지막 1회를 제외한 **27회 모두 직후에도 증상이 계속**됐다.

```

08:21:06 → 20건    08:21:53 → 19건    08:22:12 → 19건
09:12:33 → 49건    09:12:52 → 49건
15:08:00 → 11건    15:10:11 → 10건
16:45:51 → 11건

```

디스플레이 구성 재적용은 증상의 원인도 해결책도 아니다.

## 7. 미해결 — 48초 타이머의 주인

현재까지 특정하지 못한 것은 하나다: **약 48초마다 무엇이 재열거를 촉발하는가.**

가능성은 두 갈래이며, `Kernel-PnP` 220/222 이벤트의 선후 관계로 구분된다.

- 모니터가 먼저 링크를 놓는다 → `DxgKrnl` `StatusChangeNotify`가 앞선다
- 드라이버/OS가 먼저 조회를 건다 → `Kernel-PnP` 220 "Begin querying bus relations"가 앞선다

이를 잡기 위한 ETW 캡처 장치를 구성해 두었다 (9항).

## 8. EDID 변동 (기존 확인 사항, 재게재)

대기 상태에서 제품 코드가 달라진다. 시리얼은 동일.

```
정상  0x7B0C
대기  0x7B0B / 0x7B11
```

Windows는 CCD API `DISPLAYCONFIG_TARGET_DEVICE_NAME` 구조체의 `edidProductCodeId`
필드로 모니터를 식별한다. 이 값이 바뀌면 **다른 모니터가 연결된 것으로 판단**해
기존 장치를 제거하고 새 장치를 만든다. 이것이 1010 반복의 유력한 기전이다.
